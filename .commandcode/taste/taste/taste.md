# Taste
- For image editing/generation work, use the imagegen skill invoked through the codex CLI rather than ad-hoc local scripts. Confidence: 0.7
- Build public URLs against the production base `https://ilmu360.masyuk.com`. Confidence: 0.7
- Expects risk/quality claims to be justified with repo-specific verified evidence rather than generalized from a similar repo; unqualified "X is bad" framing draws pushback. Confidence: 0.5
- Judges low-likelihood/low-severity security exposure (e.g. an unauthenticated log-write endpoint) as not worth trading away working developer tooling for; prefers keeping the full dev capability, and reaffirms the call even when the risk is re-flagged. Confidence: 0.7
- Commits should be scoped to only the files changed in the current session (explicit pathspec), leaving concurrent-session work uncommitted; then push the branch. Confidence: 0.7
- Prefers tooling config as one universal, machine-wide entry that covers all sibling repos, with per-project files only as lighter overrides — asks for the "universal fix" instead of editing each repo. Confidence: 0.75
- Deploy/refresh routine should follow this order: `git fetch`/`git pull` (fast-forward), then build frontend assets, then run `./scripts/deploy.sh`, then reload Octane. Confidence: 0.6
- When a bug lives in a first-party shared package (symlinked path repo like `vendor/aiarmada/...`), fix the package source directly instead of working around it with an app-level override; also update that package's own tests. Confidence: 0.8
- Wants form labels/field names to reflect what the product actually renders (e.g. a 1:1 image shouldn't be labelled "main photo" when the 3:4 one is what shows on cards); renaming is preferred, but a field with no real consumer can be dropped outright. Confidence: 0.6
- Hero sections should use a full-bleed background image that covers the entire hero area (the pattern on /penceramah and /institusi), not a bordered card or split layout with an image panel on one side; expects new page heroes to match the existing directory-page treatment. Confidence: 0.6
- Expects an update flow to mirror its create counterpart — same field surface, order, and validation rules from one shared parameterized definition — diverging only where the lifecycle genuinely requires it; duplicated/parallel implementations of the same fields are treated as a defect. Confidence: 0.6
- When removing or renaming a feature, wants it done completely and everywhere — no backward compatibility, no deprecated aliases, no legacy shims, no leftover references (model, forms, API contract, validations, labels, MCP guards, tests) — rather than a staged or partially compatible change. Counts agent instructions/guidelines and skill docs as part of the codebase to scrub, and phrases the request as "the entire app". States this as a standing requirement even after such a change is already merged ("make sure no backward compat or legacy"), so a legacy sweep is expected by default, not only on request. Rejects "it's a declared public `Api/` interface contract with several consumers" as a justification for keeping a redundant accessor — since the app is in development and every caller is in-repo, redundancy still gets deleted. Confidence: 0.9
- For schema changes, edit the existing/original migration in place instead of adding a new additive migration (no `hasColumn`-guarded patch migration, no backfill-for-compat step); apply the same no-backward-compat, no-legacy stance to newly built features, not just removals — asks to "review and audit if this is the best way forward" before accepting a compat-preserving design. Confidence: 0.8
- A `.env` change is not enough by itself: always follow it by clearing config/route caches (`optimize:clear`) and reloading the serving layer (PHP-FPM or Octane), since cached config and long-lived workers keep stale values. Confidence: 0.85
