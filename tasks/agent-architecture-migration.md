## Ownership decisions and enduring hazards

- Directory is one combined capability for tightly related institution/person/reference/venue records; **Series belongs to Events** (`event_series`, `event_series_items`). `ModerationReview` wraps package `ModerationAction`; do not invent a moderation table.
- `ContributionEntityMutationService` (~2,100 lines) is a foreign-resource writer, not a Contributions-owned seam. Extract actual owned mutations; do not move the generic writer into Contributions or grant it foreign resources. Keep contribution approval's atomic create/verify/ownership/media/request-state behavior and post-transaction notifications.
- `User` keeps only auth scaffolding (`Notifiable`, tokens, panel gates, `globalRoles()`); I5 removed all reverse relations and the `booted()` hook (now `UserObserver`). Registration and Engagement account-lifecycle contributors are feature-registered; `HasUserRestoration` remains the account transaction/snapshot orchestrator, while Identity/Authz/framework/Affiliates restoration paths stay explicit root/package boundaries.
- The `Event` saved hook synchronously flushes pending URL/audience state through `Events\Api\EventProjections` and `SyncEventProjectionsAction` (links first, audiences second); preserve pending-bag clearing, partial-failure behavior and caller transaction boundaries. The deleting hook calls `CleanupEventAction` and the package cascade while the event row still exists. Membership, Engagement, Registration and moderation-review cleanup cross named APIs; Registration deletes nested app models leaf-first so every configured Registration audit hook runs, while Events-owned children retain their per-model hooks.
